# План реализации ЛР2 — вариант 91

## 1. Согласованные формат и правило уникальности

- Формат — JSON-массив. Каждая запись описывает одного `HumanBeing`, содержит вложенный объект `coordinates` и может содержать объект `car` с полями `name` и `cool`. Если `car` задан, машина создаётся вместе с героем. `id`, `version` и `creationDate` генерирует система.
- Имя героя должно быть уникальным среди всех героев после удаления пробелов по краям и приведения к одному регистру. Перед включением правила проверить существующие данные на дубли.

## 2. Загрузка и атомарный импорт

- Добавить авторизованный `POST /api/imports`, принимающий файл через `multipart/form-data`. Ограничить размер файла и число записей. Для ошибок в записи возвращать её номер, поле и причину.
- Переиспользовать серверные ограничения ЛР1 для героя, координат и машины. Валидировать структуру и значения перед записью, а проверки, зависящие от состояния БД, выполнять внутри транзакции.
- Сохранять всех героев и машины из файла в одной транзакции. Проверить откат на ошибке, возникающей после начала записи: в БД не должно остаться ни одного объекта из файла. Обновлять списки через пакетное WebSocket-уведомление после успешного коммита.

## 3. История импорта и роли

- Ввести роли `USER` и `ADMIN`. При регистрации назначать `USER`, роль администратора выдавать отдельно.
- Добавить таблицу операций импорта. Для каждой попытки, принятой приложением от авторизованного пользователя, создавать запись с ID операции, инициатором и начальным статусом. Сохранять её отдельной транзакцией до разбора файла, чтобы в историю попадали и ошибки формата или валидации.
- Статус `SUCCESS` и количество добавленных героев фиксировать в транзакции импорта. При ошибке после отката отдельной транзакцией обновлять ту же запись до `FAILED`, оставляя количество пустым. Повторы транзакции при конфликте изоляции относятся к одной операции истории.
- Через `GET /api/imports` возвращать обычному пользователю только его операции, а администратору — все. Проверять доступ на сервере по текущей сессии.
- Добавить в React раздел «Импорт» с формой загрузки и таблицей истории. Показывать ID, статус, инициатора и количество героев только для успешных операций. Расширить API-клиент для отправки `FormData`.

## 4. Уникальность и конкурентные изменения

- Проверять уникальность в бизнес-логике создания, редактирования и импорта. При импорте искать совпадения в файле и среди сохранённых героев. При редактировании исключать из проверки самого героя. Не добавлять для нового правила ограничение `UNIQUE` в PostgreSQL или ORM.
- Сохранить существующий `@Version` для обновления. Передавать ожидаемую версию и при удалении, чтобы устаревшее подтверждение не удалило уже изменённого героя. Проверить конфликт между чтением и записью и обработку случая, когда объект уже удалён.
- Первую проверку конкурентной уникальности провести на уровне изоляции по умолчанию. Проверить фактический уровень в транзакции через `SHOW transaction_isolation`. Если две транзакции успевают проверить отсутствие имени и обе его записывают, проверить `SERIALIZABLE` для создания, редактирования и импорта. При `40001` ограниченно повторять целиком транзакцию записи, а подтверждённый дубликат возвращать как `409 Conflict`. Менять уровень только для операций, где исходный прогон выявил аномалию.

## 5. JMeter и порядок прогонов

- Подготовить один параметризованный `.jmx` для тестовой БД. Использовать отдельные аккаунты и HTTP-сессии. Конфликтующие запросы запускать одновременно через `Synchronizing Timer` с таймаутом. Проверять ответы и итоговое состояние данных.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Создание, редактирование и удаление | Все операции доступны, итоговое состояние совпадает с ожидаемым |
| Успешный и неудачный импорт | Успех сохраняет весь файл и верное число героев. Неудача оставляет строку `FAILED` без количества и не создаёт героев или машин |
| Два обновления одной версии; обновление и удаление одного героя | Нет потерянного обновления. Устаревший запрос получает конфликт или `404`, если объект уже удалён |
| Два создания с одним именем; создание одновременно с импортом того же имени | После обоих запросов остаётся ровно один герой с этим именем |
| История от имени двух пользователей и администратора | Каждый пользователь видит свои попытки, администратор видит все |

1. Прогнать сценарий с уровнем изоляции по умолчанию. Записать фактический уровень, параметры, результаты и конечное состояние данных.
2. Если выявлена аномалия, изменить изоляцию только для затронутых операций и повторить тот же сценарий на таком же исходном наборе данных с теми же параметрами. Если аномалии нет, сохранить исходный уровень.
