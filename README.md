# Информационные системы. Лабораторная работа №2 (вариант 91)

Учебная информационная система управления коллекцией объектов `HumanBeing`
(с вложенными `Coordinates` и связанной сущностью `Car`) — CRUD, серверная
пагинация/фильтрация/сортировка, real-time синхронизация между клиентами.

**Стек:** Jakarta EE 8 (javax.*), CDI, JAX-RS, Java WebSocket API, Hibernate/JPA, PostgreSQL, WildFly 21.

## Real-time синхронизация

Изменения одного пользователя сразу видны у остальных — без перезагрузки страницы:

- сервис после успешного commit публикует CDI-событие `DataChangedEvent` (`AFTER_SUCCESS`);
- наблюдатель рассылает всем открытым WebSocket-сессиям (`/ws/changes`) короткий сигнал
  `{"entity":"human","change":"updated","id":42}` — без самих данных; массовые спецоперации дают один сигнал `bulk`;
- клиент по сигналу перезапрашивает по REST то, что у него на экране (страница таблицы с текущими пагинацией,
  сортировкой и фильтрами, список машин); пачка сигналов склеивается в один запрос;
- соединение восстанавливается само (экспоненциальная задержка до 30 с), после переподключения данные перезапрашиваются;
  состояние видно по индикатору в шапке;
- если открытого героя изменил или удалил другой пользователь, форма не перезаписывается молча: показывается уведомление.


## Быстрый старт

1. Для новой PostgreSQL последовательно применить `sql/schema.sql`, `sql/users.sql`, `sql/functions.sql` и `sql/lab2.sql`. Для существующей БД ЛР1 применить только `sql/lab2.sql`. Скрипт `schema.sql` пересоздаёт таблицы героев и машин.
2. Настроить datasource в `DatasourceConfig.java` под свою БД. URL можно переопределить параметром запуска WildFly `-Dlab.db.url=jdbc:postgresql://127.0.0.1:55432/lab2`. Для этого в подсистеме `ee` должно быть включено `annotation-property-replacement`.
3. `mvn clean package` → задеплоить `target/lab-is.war` на WildFly. Юнит-тесты (рассылка WebSocket) — `mvn test`.

## Фронтенд (UI)

React + TypeScript + Vite, исходники в `frontend/`. Собранная статика попадает в корень war и открывается по корню контекста
(`http://host:8080/lab-is/`). Node.js нужен только для сборки (20.19+ или 22.12+), на сервере его нет.

| Задача | Команда |
| --- | --- |
| Разработка (Vite + proxy `/api` на локальный WildFly) | `cd frontend && npm install && npm run dev` → http://localhost:5173 |
| Сборка статики в `frontend/dist` (с проверкой типов) | `cd frontend && npm run build` |
| Сборка war со встроенным UI | `mvn clean package` (после `npm run build`) |

Адрес бэкенда для dev-режима по умолчанию `http://localhost:8080/lab-is`; другой задаётся в `frontend/.env.local`:
`BACKEND_URL=http://localhost:8080/другой-контекст`.
Порядок для деплоя: `npm run build` → `mvn clean package` → `target/lab-is.war` на WildFly. Если `frontend/dist` не собран,
Maven соберёт war без UI.

## Импорт героев

В разделе «Импорт» выберите JSON-файл в UTF-8 размером до 1 МиБ. Файл содержит от 1 до 500 записей.

```json
[
  {
    "name": "Arthur Dent",
    "coordinates": { "x": 10.5, "y": 22 },
    "realHero": true,
    "hasToothpick": false,
    "mood": "GLOOM",
    "impactSpeed": 42,
    "weaponType": null,
    "car": { "name": "Lada Kalina", "cool": true }
  }
]
```

`car` можно опустить или передать как `null`. Если объект передан, машина создаётся вместе с героем. Поля `name` и `cool` машины допускают `null`. `weaponType` необязателен. Поля `id`, `version` и `creationDate` генерирует система. Имена героев уникальны после `String.strip()` и `toLowerCase(Locale.ROOT)`. Перед обновлением существующей БД проверьте имена по тому же правилу и устраните совпадения. Тестовая база перед замерами была пустой.

`POST /api/imports` принимает файл в поле `file` формы `multipart/form-data`. Любая ошибка откатывает весь набор героев и машин. Запись операции существует независимо от транзакции записи данных. При откате она получает статус `FAILED`, при коммите — `SUCCESS` и количество добавленных героев. `GET /api/imports?offset=0` возвращает историю постранично. Пользователь видит свои операции, администратор — все.

Регистрация выдаёт роль `USER`. Для назначения администратора оператор БД выполняет `UPDATE app_user SET role = 'ADMIN' WHERE username = 'имя_пользователя';`.

## Проверка транзакций в JMeter

Сценарий — [jmeter/lab2.jmx](jmeter/lab2.jmx), контрольные запросы — [jmeter/lab2.groovy](jmeter/lab2.groovy). Прогоны выполнены на PostgreSQL 16.6, WildFly 21.0.2.Final, JDK 11 и JMeter 5.6.3.

1. Разверните приложение на отдельной тестовой БД. Создайте аккаунты `lab_a`, `lab_b` и `lab_admin` с одним тестовым паролем. Назначьте `lab_admin` роль `ADMIN`.
2. Примените [jmeter/observe-isolation.sql](jmeter/observe-isolation.sql) только к тестовой БД. Триггер добавляет 100 мс к созданию или переименованию тестового героя, чтобы запросы гарантированнее пересекались, и записывает уровень изоляции прямо в транзакции записи. Оба прогона используют этот же триггер.
3. Каждый прогон начинайте с пустых таблиц героев, машин, импорта и наблюдений, сохраняя тестовые аккаунты. Для сравнения разверните `b319b1f` для исходного прогона и `5b14f64` для повторного.
4. Из корня проекта запустите JMeter. На Windows используйте `jmeter.bat` и задайте переменную окружения через PowerShell.

```bash
export LAB2_TEST_PASSWORD='пароль_тестовых_аккаунтов'
jmeter -n -t jmeter/lab2.jmx -Jscript="$PWD/jmeter/lab2.groovy" \
  -JbaseUrl=http://127.0.0.1:8180/lab-is -Jiterations=15 -Jrun=isolation \
  -l target/jmeter-results.jtl -j target/jmeter-run.log
```

Опциональные параметры `-JuserA`, `-JuserB` и `-Jadmin` заменяют имена аккаунтов. В каждом прогоне два потока запускаются без разгона, у каждого своя HTTP-сессия. Конкурирующие запросы выравниваются на `Synchronizing Timer` с таймаутом 90 секунд. Строки `verify` в JTL содержат коды ответов и число сохранившихся объектов. Фактическую изоляцию можно сверить по таблице наблюдений.

```sql
SHOW transaction_isolation;
SELECT operation, isolation, count(*)
FROM lab2_isolation_observation
GROUP BY operation, isolation
ORDER BY operation, isolation;
```

### Результаты двух прогонов

Оба прогона начались с 0 героев, использовали 2 потока, 15 итераций и одинаковые данные и параметры. Для гонок за имя в таблице показано число итераций, в которых нарушилась уникальность.

| Проверка | До, `READ COMMITTED` | После, `SERIALIZABLE` для записи имён |
| --- | --- | --- |
| Два создания с одним нормализованным именем | 15/15: два `201`, два героя | 0/15: `201` и `409`, один герой |
| Два переименования разных героев в одно имя | 15/15: два `200`, два героя с новым именем | 0/15: `200` и `409`, один герой с новым именем |
| Создание одновременно с импортом того же имени | 15/15: два `201`, два героя | 0/15: `201` и `409`, один герой |
| Два обновления одной версии | 15/15: одно `200`, второе `409` | 15/15: одно `200`, второе `409` |
| Обновление одновременно с удалением | Во всех 15 парах победило удаление (`204`), обновление получило `409` или `404` | Во всех 15 парах победило удаление (`204`), обновление получило `404` |
| Откат после начала записи, валидация и видимость истории | 15/15 итераций прошли | 15/15 итераций прошли |
| Сэмплы JMeter с ошибками | 15 из 210 | 0 из 210 |

Тестовый триггер зафиксировал `read committed` у 180 закоммиченных вставок и 60 обновлений в исходном прогоне. В повторном он зафиксировал `serializable` у 150 вставок и 45 обновлений. Снижение соответствует устранению 30 лишних вставок и 15 лишних переименований. История после повторного прогона содержала 18 успешных и 57 неудачных операций, по одной строке на каждый из 75 запросов загрузки.

### Почему изменена изоляция

- **Конфликт на одном герое.** Сервер сравнивает присланную версию с текущей при обновлении и удалении. JPA использует `@Version` в условии записи и обнаруживает изменение, случившееся после этого сравнения. Базовый прогон подтвердил защиту при `READ COMMITTED`. Когда запись уже удалена к моменту чтения, запрос получает `404`.
- **Конфликт имён у разных героев.** При `READ COMMITTED` обе транзакции могли прочитать, что имя свободно, и записать две разные строки. Версии этих строк независимы. Поэтому создание, редактирование и запись импорта начинают отдельную JTA-транзакцию с `SET TRANSACTION ISOLATION LEVEL SERIALIZABLE` до первого чтения или записи. При SQLSTATE `40001` выполняется до четырёх попыток всей транзакции, включая проверку имени. Когда имя уже занято, приложение возвращает `409`. Нового ограничения `UNIQUE` в БД нет. [Документация PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html)
- Настройка PostgreSQL по умолчанию остаётся `READ COMMITTED`. Чтение, удаление, операции истории и другие операции, не способные занять имя, используют исходную изоляцию. Фиксация успеха импорта входит в транзакцию записи импорта.
